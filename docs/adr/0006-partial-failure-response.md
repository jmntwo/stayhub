# ADR 0006. 부분 실패 표현

- 상태: 확정
- 날짜: 2026-09-13

## 배경

검색 한 건이 여러 공급사를 병렬 조회하므로 일부만 실패하는 경우가 정상 상황임. 일부 공급사 조회가 실패했다면 그 사실이 응답에서 드러나야 함

## 검토했다 폐기한 대안

- **전부 실패에 HTTP 503**: 클라이언트가 200일 때의 결과 구조와 503일 때의 오류 구조를 따로 처리해야 함. 우리 서비스는 정상인데 서비스 불가로 보임
- **응답 헤더로 표기**: 본문만 보는 클라이언트가 놓침
- **항목마다 실패 플래그**: 실패한 공급사는 항목 자체가 없어서 표기할 자리가 없음

## 결정

- 공급사 쪽 실패는 전부 HTTP 200. 요청은 유효했고 검색은 수행됐으므로 결과의 속성으로 표현
- 본문 최상위에 `suppliers` 배열. 공급사마다 한 요소

| 필드 | 값 |
|---|---|
| supplier | A, B |
| status | OK, PARTIAL, FAILED |
| reason | TIMEOUT, UNAVAILABLE, REJECTED, NO_MAPPING |

- status 판정. 청크 전부 성공이면 OK, 일부 실패면 PARTIAL, 전부 실패면 FAILED. 매핑이 없으면 FAILED + NO_MAPPING
- TIMEOUT은 연결·응답 타임아웃, UNAVAILABLE은 5xx·E5xx·연결 실패, REJECTED는 4xx·E4xx
- 전부 실패도 200 + 빈 `items` + 모두 FAILED
- 우리 API 자체의 잘못된 요청은 400 (200 통일은 공급사 쪽 실패에만 해당)

## 결과

- 클라이언트는 상태 코드와 무관하게 한 가지 본문 구조만 처리
- 성공, 부분 실패, 전부 실패, 매핑 미확보가 같은 자리에 같은 어휘로 표현됨
- 비용 1: HTTP 상태 코드 기준 오류율 지표에 공급사 장애가 잡히지 않음. 공급사별 지표를 따로 두어 보완 예정
- 비용 2: PARTIAL일 때 어느 숙소가 빠졌는지는 응답에서 알 수 없음. 청크 단위 상세는 로그와 지표로
