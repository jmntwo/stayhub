# ADR 0007. 어댑터의 책임 범위

- 상태: 확정
- 날짜: 2026-09-14

## 배경

어댑터는 공급사 API를 호출하고 응답을 표준 모델로 바꾸는 층. 검색 결과 항목(StayOffer)에는 내부 식별자와 매핑 테이블의 이름, 최대 인원이 들어가야 하는데 이 값은 DB에 있음

## 검토했다 폐기한 대안

- **어댑터가 매핑 테이블을 조회해 StayOffer를 완성**: 어댑터가 리포지토리에 의존. 변환 테스트에 DB가 필요하고, 공급사 연동 계층이 저장소 계층까지 알게 됨

## 결정

- 어댑터는 형식만 정규화. 요금 총액, 가용 객실 수, 조식 여부까지 계산하고 식별자는 공급사 코드 그대로 둔 중간 모델(SupplierOffer, CatalogEntry) 반환
- 내부 식별자, 이름, 최대 인원 결합은 검색 서비스가 매핑 테이블을 조회해 수행
- 변환 계산은 어댑터에서 분리한 package-private 클래스(SupplierANormalizer, SupplierBNormalizer)에 둠
- 어댑터는 요청에 없던 코드가 응답에 섞여 와도 걸러내지 않음 (결합 단계의 몫)
- 청크 분할(최대 50개)은 호출하는 쪽 책임. 어댑터는 초과 시 즉시 거절

## 결과

- 어댑터 테스트가 순수해짐. 정규화는 record 생성만으로, 연동은 WireMock만으로
- 신규 공급사 추가 시 DB를 몰라도 어댑터를 쓸 수 있음
- 비용: StayOffer 외에 중간 모델 SupplierOffer 필드 대부분이 겹침

## AI 제안과 내 판단

- AI가 두 방식을 비교해 "형식만 정규화" 쪽을 추천했고, 어댑터가 DB를 모르는 편이 테스트와 경계에 유리하다고 판단해 수용
- 정규화 클래스 분리도 AI 제안. 테스트 편의를 위한 것임을 확인한 뒤 수용
