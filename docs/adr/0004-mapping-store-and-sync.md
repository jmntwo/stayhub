# ADR 0004. 매핑 저장소와 동기화 전략

- 상태: 확정
- 날짜: 2026-09-12

## 배경

- 저장 대상은 공급사 코드 ↔ 내부 식별자 매핑뿐. 요금, 재고는 외부에 있으므로 저장하지 않음
- 매핑은 공급사 숙소 목록 API를 호출해 만듦. 목록은 자주 바뀌지 않고, 요금, 재고는 매번 바뀜
- 외부 연동은 실패한다는 전제로 설계해야 함
- README의 실행 절차만으로 실행되어야 함. 절차를 짧게 유지하는 것을 목표로 함

## 검토했다 폐기한 대안

저장소

- **MySQL + docker-compose**: 자주 사용해서 손에 익은 방식. 그러나 Docker 등 실행 환경을 요구. 매핑 실패 대응 범위는 파일 모드와 같고, 저장소 신뢰성이라는 별도 장점만 있음
- **H2 파일 모드**: 처음 선택. 상대 경로가 실행 주체(Gradle은 app/, IDE는 루트)에 따라 갈려 파일이 두 곳에 생김. 경로를 고정하면 해결되지만, 아래 비교에서 인메모리 대비 이득이 한 상황뿐이고 오래된 매핑 위험이 추가됨

동기화 시점

- **검색할 때마다 목록 조회**: 항상 최신이지만 잘 바뀌지 않는 목록을 매 검색마다 호출. 낭비
- **기동 시 1회만**: 서버는 재시작을 전제로 운영되지 않음. 따라서 그 사이 추가된 숙소, 객실 타입이 검색에서 빠지는 문제

### 저장소별 매핑 실패 대응 비교

| 상황 | 인메모리 | 파일 / MySQL |
|---|---|---|
| 첫 실행인데 목록 API 장애 | 매핑 없음 | 매핑 없음. 채운 적이 없음 |
| 실행 중 주기 갱신 실패 | 기존 매핑 유지 | 기존 매핑 유지 |
| 재시작인데 목록 API 장애 | 매핑 없음. 재시도로 복구 | 이전 매핑으로 검색 가능 |
| 공급사가 삭제한 숙소 | 다음 갱신까지 코드 전송 | 동일. 오래될수록 빈도 증가 |

차이는 세 번째 상황 하나. 영구 저장소는 오래됐을 수 있는 매핑으로라도 응답(가용성 우선), 인메모리는 그 공급사 없이 응답하고 실패를 드러냄(정확성 우선). **검색 응답에서 공급사 조회 실패를 드러내야 한다는 원칙과 같은 방향으로 후자를 택함**

## 결정

저장소

- H2 인메모리 (jdbc:h2:mem:stayhub)
- 스키마는 당분간 ddl-auto: update. 매핑 테이블 확정 후 validate + 스키마 파일 전환 재검토
- H2 콘솔 활성화 (/h2-console)

동기화 시점

- 기동 시 매핑이 비어 있으면 즉시 1회 동기화. 빈 상태 방지가 목적
- 이후 주기 갱신이 본체. 주기는 설정값으로 두고 기본 6시간. 목록 변경 빈도 대비 호출 비용을 기준으로 정함

갱신 시 데이터 처리

- 같은 (공급사, 코드)는 항상 같은 내부 식별자. upsert로 처리
- 새 숙소 및 객실 타입은 추가. 목록에서 사라진 상품은 삭제하지 않고 비활성화
- 주기 갱신 실패 시 기존 매핑 유지

기동 시 목록 API 장애 대응

- 동기화 실패를 기동 실패로 만들지 않음. 앱은 뜨고 로그와 상태만 남김
- 동기화 실패 시 짧은 간격으로 몇 번 재시도(백오프). 그래도 실패하면 다음 정규 주기까지 대기
- 매핑이 비어 있으면 횟수 제한 없이 짧은 간격 재시도 유지
- 공급사별 독립 동기화 (A 목록 실패가 B 동기화를 막지 않음)
- 매핑이 없는 공급사는 검색 응답의 부분 실패 표기로 드러냄

## 결과

- clone 후 추가 설정 없이 실행되고 파일이 남지 않음
- 테스트도 같은 인메모리 설정 사용. 별도 테스트 DB 불필요
- 목록은 미리 확보하고 가끔 갱신, 요금, 재고는 검색 시 실시간 조회. 두 API의 성격 차이가 그대로 구조에 반영됨
- 비용 1: 재시작 직후 목록 API가 장애면 그 공급사 상품이 재시도 성공까지 검색에서 빠짐
- 비용 2: 갱신 주기 사이에 공급사가 삭제한 숙소 코드가 재고 조회에 섞여 나감. 알 수 없는 코드가 섞여도 나머지 결과를 살리는 처리가 견고성 설계에 필요

## AI 제안과 내 판단

- AI가 H2를 추천. 이유를 되물어 실행 마찰, DB 역할, 테스트 단순화라는 근거와 단점을 확인한 뒤 수용
- "실패 전제라면 파일로 대비하는 것이 낫지 않나" 검토. 위 비교표가 그 결과. 영구 저장소의 이득이 한 상황뿐이고 재시도로 대체 가능하다고 판단 + 매핑 단계도 실패를 숨기지 않고 드러내는 쪽이 부분 실패 노출 원칙과 일관된다고 판단해 인메모리 확정
