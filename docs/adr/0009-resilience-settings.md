# ADR 0009. 견고성 설정값과 재시도 및 서킷 설계

- 상태: 확정 (재시도, 서킷, 가상 스레드는 설계만)
- 날짜: 2026-09-15

## 배경

외부 연동은 실패한다는 전제. 견고성 필수 항목은 병렬 호출, 타임아웃, 부분 실패 허용, 실패 판정 통일이고, 타임아웃 값은 왜 그렇게 정했는지 설명해야 함. 재시도 정책과 서킷 브레이커는 선택 항목

값을 정하는 기준: 고객이 검색 결과를 기다리는 시간의 상한 안에서 살아 있는 공급사의 결과는 반드시 내보내기

## 검토했다 폐기한 대안

- **응답 타임아웃 하나만 두고 공급사 전체 상한은 없음**: 청크가 여러 개면 호출 하나하나는 3초 안에 끝나도 청크가 줄줄이 밀려 공급사 전체로는 몇십 초가 될 수 있음. 공급사 단위 상한이 따로 필요
- **데드라인을 검색 요청 전체에 한 번 (`block(deadline)`)**: 데드라인에 걸리면 이미 도착한 다른 공급사의 결과까지 함께 버려짐. 공급사 단위에 걸어야 부분 실패로 처리됨
- **청크 동시 수 무제한**: 숙소가 수천 개면 청크 수십 개가 한 번에 나가 공급사 호출 한도(429)에 걸림

## 결정

설정값 (application.yaml, 전부 변경 가능)

| 항목 | 값 | 근거 |
|---|---|---|
| 연결 타임아웃 | 1초 | 공급사 서버가 살아 있으면 연결은 수십 ms. 1초를 넘기면 죽은 것으로 판정해도 손해가 없음 |
| 응답 타임아웃 | 3초 | 재고·요금 조회는 공급사 DB 조회 한 번. 정상이면 1초 안. 3초는 "느린 정상"과 "장애"의 경계 |
| 공급사 데드라인 | 5초 | 고객 대기 상한. 응답 타임아웃 3초에 청크가 순차로 밀리는 여유 2초. 공급사 단위로 걸어 넘기면 그 공급사만 TIMEOUT |
| 청크 크기 | 50 | 공급사 API 상한 |
| 공급사별 동시 청크 수 | 4 | 한 번에 숙소 200개분 요청. 지금 규모(숙소 4개, 청크 1개)에서는 의미 없고 수천 개 규모를 위한 상한 |

세 층의 관계

```
연결 1초 < 응답 3초 < 공급사 데드라인 5초 < block 상한 6초
```

- 정상: 공급사 응답이 1초 안에 와 어느 층에도 닿지 않음
- 공급사 무응답: 3초에 어댑터가 TIMEOUT 예외 → 그 청크 실패 → 다른 공급사 결과와 병합해 약 3초에 응답
- 청크가 많아 3초 안에 다 못 끝남: 5초에 그 공급사만 TIMEOUT. 다른 공급사는 영향 없음
- block 상한 6초는 위 층이 전부 동작한다는 전제에서 닿을 일이 없는 최후 안전장치

재시도 (설계만)

- 대상: FailureReason.retryable이 true인 실패(TIMEOUT, UNAVAILABLE)만
- 방식: 어댑터의 fetchAvailability Mono에 `retryWhen`으로 1회
- 지금 값으로는 켜도 효과 없음: 응답 타임아웃 3초 × (첫 호출 + 재시도 1회) = 6초인데 공급사 데드라인이 5초라 재시도 도중 잘림
- 켜려면 값을 함께 조정: 응답 타임아웃을 2초로 낮추거나(2 + 2 = 4초 < 5초), 데드라인을 7초 이상으로 늘림. 전자는 느린 정상을 오판할 위험이 커지고 후자는 고객 대기가 길어짐
- 429는 현재 REJECTED로 두어 재시도하지 않음. 구현한다면 별도 사유로 떼어 백오프 재시도 대상으로
- 미구현 이유: 필수 네 가지가 먼저이고, 위 값 조정이 따라오는 결정이라 일정 안에서 검증할 시간이 없다고 판단

서킷 브레이커 (설계만)

- 공급사 단위. 최근 N회 중 실패 비율이 임계를 넘으면 일정 시간 호출을 건너뛰고 즉시 FAILED로 응답
- 효과: 죽은 공급사에 매 검색마다 3초를 쓰는 대신 즉시 실패해 응답이 빨라지고 공급사 회복을 방해하지 않음
- 도구: Resilience4j CircuitBreaker (Boot 4용 아티팩트 존재 확인). 상태는 SyncStatus처럼 메모리

스레드 점유 (설계만)

- MVC + block 구조는 검색 요청마다 서블릿 스레드 하나가 최대 데드라인만큼 대기 (ADR 0003 비용)
- Java 21 가상 스레드(`spring.threads.virtual.enabled=true`)를 켜면 대기 중 OS 스레드를 점유하지 않아 이 비용이 대부분 사라짐. WebClient block()과 JPA가 가상 스레드에서 문제없이 도는지 검증 후 적용

## 결과

- 공급사 하나가 무응답이어도 검색은 약 3초 안에 응답
- 청크가 많아 한 공급사가 오래 걸려도 5초를 넘기지 않음. 공급사 데드라인에서 그 공급사만 TIMEOUT 처리
- 값이 전부 application.yaml에 있어 공급사 특성에 맞춰 코드 수정 없이 조정 가능 (예: 응답이 원래 느린 공급사는 응답 타임아웃만 늘림)
- 비용 1: 정상인데 느린 응답(3초 초과)을 장애로 오판함. 그 검색에서 해당 공급사 상품이 빠짐. 타임아웃을 늘리면 오판은 줄지만 고객이 그만큼 더 기다림
- 비용 2: 현재는 재시도/서킷이 없어 죽은 공급사에도 검색마다 3초를 씀
- 비용 3: 청크 동시 수 4는 수천 개 규모에서만 의미가 있는 값이라 실제 부하로 검증하지 못한 추정치

## AI 제안과 내 판단

- AI가 1초, 3초, 5초와 역산 논리를 제안. 값 자체보다 세 층의 관계와 근거가 중요하다고 보고 수용. 값은 수정가능하도록 설정으로 뺌
- 데드라인 위치는 AI가 공급사 단위를 제안. 검색 전체에 걸면 도착한 결과까지 버려진다는 점에서 수용
